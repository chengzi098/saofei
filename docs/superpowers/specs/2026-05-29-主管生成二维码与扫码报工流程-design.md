> 状态：已确认，待实现

## 1. 设计概述

### 1.1 背景

原需求文档中，二维码生成由"老板录入裁剪信息"触发，系统自动分扎并生成二维码。经与橙子讨论，调整为**主管负责生成二维码**，且二维码对应的是**一扎货**（而非原设计的"订单+工序组合"）。工人扫码后从该扎货的所有工序中选择自己完成的工序进行报工。

### 1.2 核心变更点

| 原设计 | 新设计 |
|--------|--------|
| 老板录入裁剪信息触发分扎 | 主管手动逐扎录入 |
| 系统自动按固定数量分扎 | 主管自由输入每扎数量 |
| 每扎自动生成唯一二维码 | 主管确认后生成二维码 |
| 扫码自动带出订单+工序信息 | 扫码后显示工序列表，工人手动选择 |
| 款式工序在裁剪时固定 | 主管分扎时可从模板选用并增删改 |

### 1.3 参与角色

- **老板**：预先定义款式和工序模板
- **主管**：分扎、调整工序、生成二维码、审核报工
- **工人**：扫码、选择工序、提交报工

## 2. 数据模型

### 2.1 新增表：扎货工序表 `bundle_process`

每扎货有多少道工序，就生成多少条记录（从款式模板复制，主管可调整）。

```sql
CREATE TABLE bundle_process (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    company_id BIGINT NOT NULL COMMENT '公司ID',
    bundle_id BIGINT NOT NULL COMMENT '所属扎货ID',
    process_id BIGINT COMMENT '关联的款式工序ID（可为空，主管手动添加时无关联）',
    process_name VARCHAR(50) NOT NULL COMMENT '工序名称（快照）',
    process_price DECIMAL(10,2) NOT NULL COMMENT '工序单价（快照）',
    seq_no INT NOT NULL COMMENT '工序顺序号',
    status TINYINT DEFAULT 0 COMMENT '0=未开始, 1=进行中, 2=已完成',
    deleted TINYINT DEFAULT 0 COMMENT '逻辑删除：0=未删, 1=已删',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_bundle_id (bundle_id),
    INDEX idx_company_id (company_id)
) COMMENT='扎货工序表';
```

## 3. 业务流程

### 3.1 主流程：从收货到工资

```
老板：创建款式 + 定义标准工序模板（裁剪→缝纫→整烫→质检）
        ↓
收到货物
        ↓
主管：创建扎货
        ├── 输入：扎号、数量
        ├── 选择款式 → 自动带出标准工序列表
        ├── 可调整工序：增删改、调顺序
        └── 确认 → 系统生成二维码 + 扎货工序记录
        ↓
打印二维码标签 → 贴货上
        ↓
工人：扫码
        ├── 显示：这扎货的工序列表（未开始的才能选）
        ├── 勾选：自己做的工序（可多选）
        ├── 系统检查：上一道工序是否已完成？
        │   └── 否 → 弹警告"上一道XX工序未完成，确定要报工？"
        └── 确认提交 → 生成待审核报工记录
        ↓
主管：报工审核
        ├── 列表显示：本班组所有待审核报工
        ├── 批量操作：勾选多条 → 一键通过
        └── 单条操作：通过 / 改部分数量 / 驳回 / 写备注
        ↓
审核通过 → 计算工资 + 更新工序状态
        ↓
全部工序完成 → 老板出货 → 二维码失效
```

### 3.2 子流程：补报

```
工人忘记报工 → 次日扫码提交 → 标记为"补报"
        ↓
主管在"补报"标签页单独查看 → 补报记录标红显示
        ↓
主管审核通过 → 正常计入工资
```

### 3.3 子流程：返工

```
某扎货已完成 → 发现质量问题需要返工
        ↓
主管在扎货详情页点击"返工"
        ↓
原二维码失效 → 重新生成分扎和二维码
        ↓
新二维码重新走完整流程
```

### 3.4 子流程：审核后修改

```
主管审核通过 → 发现数量错误
        ↓
主管点击"撤回" → 报工记录状态变回"待审核"
        ↓
重新审核（改数量 / 驳回 / 通过）
```

## 5. 业务规则

### 5.1 二维码规则

| 规则 | 说明 |
|------|------|
| 生成时机 | 主管确认分扎信息后立即生成 |
| 内容格式 | `BUNDLE_{id}` 或其他唯一标识，扫码后解析为扎货ID |
| 重新打印 | 主管在"二维码管理"页找到该扎，点击"重新打印"，内容不变 |
| 失效条件 | 1. 老板点击"出货"；2. 主管手动标记失效；3. 返工后原码失效 |
| 全部完成后 | 不自动失效，需老板出货或主管手动操作 |

### 5.2 工序顺序规则（半严格）

| 场景 | 系统行为 |
|------|---------|
| 工人选后面的工序 | 系统检查上一道是否已完成 |
| 上一道未完成 | 弹警告提示"上一道XX工序未完成，确定要报工？" |
| 工人确认 | 仍可提交，报工记录标黄 |
| 主管审核 | 标黄的报工记录特别显示，主管重点检查 |

### 5.3 数量控制规则

| 场景 | 系统行为 |
|------|---------|
| 默认报工 | 按扎内全部数量计算 |
| 部分完成 | 主管审核时输入实际数量（如10件/扎20件） |
| 数量释放 | 剩余数量变为"未开始"状态，其他工人可继续报 |
| 多人报同一道 | 允许多人报，分别记录，分别审核 |

### 5.4 数据隔离规则

| 规则 | 说明 |
|------|------|
| 主管看扎货 | 只能看到 `creator_id = 自己` 的扎货 |
| 主管看报工 | 只能看到本班组（`team_id`）的报工记录 |
| 工人扫码 | 不受班组限制，任何工人扫任何有效二维码都能报工 |

### 5.5 超时提醒规则

| 条件 | 行为 |
|------|------|
| 触发条件 | 扎货创建后72小时无任何报工记录 |
| 显示方式 | 扎货进度看板中该扎标红 |
| 通知方式 | 主管进入页面时显示提醒数字 |

## 6. 关键接口设计（概要）

### 6.1 主管端

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/bundle` | POST | 创建扎货（含工序列表） |
| `/api/bundle/{id}/qr-code` | GET | 获取二维码内容（支持重新打印） |
| `/api/bundle` | GET | 主管的扎货列表（含进度） |
| `/api/work-record/review` | PUT | 审核报工（通过/驳回/改数量） |
| `/api/work-record/review/batch` | PUT | 批量审核通过 |
| `/api/work-record/{id}/withdraw` | PUT | 撤回已审核的报工 |
| `/api/bundle/{id}/return` | POST | 发起返工（原码失效，生成新扎） |

### 6.2 工人端

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/bundle/scan/{qrCode}` | GET | 扫码获取扎货工序列表 |
| `/api/work-record` | POST | 提交报工（可多选工序） |
| `/api/work-record/me` | GET | 查看我的报工记录 |
